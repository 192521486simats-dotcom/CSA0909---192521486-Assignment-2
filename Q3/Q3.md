1. Inputs and Outputs
Problem context: A college fest records student attendance by scanning ID cards at multiple entry gates. The same student may be scanned more than once. The system uses HashSet<Student> to store only unique students.
A junior developer has implemented equals() but has not overridden hashCode().
Input:
•	Student registration number.
•	Student name.
•	Attendance scans from different gates.
•	Multiple scans of the same student.
Output:
•	Unique student records.
•	Number of unique students.
•	Comparison between the incorrect and corrected implementations.
Objective: Understand how equals() and hashCode() work together in hash-based collections and prevent duplicate student records.

2. Prediction and Design Reasoning
Understanding equals()
The equals() method compares two objects to determine whether they are logically equal.
For this attendance system, two Student objects should be considered equal if they have the same registration number.
Example:
Student s1 = new Student("192311001", "Arun");
Student s2 = new Student("192311001", "Arun");

System.out.println(s1.equals(s2));
Output:
true
Understanding hashCode()
The hashCode() method returns an integer hash value for an object. HashSet uses this value to help determine where an object belongs internally.
The important contract is:
•	If two objects are equal according to equals(), they must return the same hash code.
•	Two unequal objects may have the same hash code.
•	Overriding equals() without correctly overriding hashCode() can cause problems in HashSet and HashMap.
Prediction before implementation

Test	Input	Predicted set size
Test 1	Add the exact same object twice	1
Test 2	Add two different objects with the same registration number and one different student	Usually 3 with the faulty implementation
Test 3	Change a registration number after insertion	Lookup may fail with a mutable hash-based key

Reasoning:
In Test 1, the same object reference is added twice. HashSet recognizes that it is already present.
In Test 2, two different Student objects have equal registration numbers, but the faulty class uses the default identity-based hash code. They can be placed in different hash buckets, so the duplicate may not be detected.
In Test 3, changing a field used to calculate the hash code after insertion can make the object difficult to locate in the HashSet.
3. Experimental Design
Three experiments are designed.
Experiment 1 – Same object scanned twice
•	Create one Student object.
•	Add the same object twice.
•	Check the HashSet size.
•	Expected size: 1.
Experiment 2 – Duplicate registration number
•	Create two separate Student objects with the same registration number.
•	Add both objects to the HashSet.
•	Add one more student with a different registration number.
•	Compare the result before and after overriding hashCode().
Experiment 3 – Changing registration number
•	Create a Student object.
•	Add it to the HashSet.
•	Change the registration number used for hashing.
•	Check whether contains() can still locate the object.
This experiment demonstrates why fields used in equals() and hashCode() should not be modified while an object is stored in a hash-based collection.

Why do duplicates appear?
HashSet internally uses the hash code to identify the bucket in which an object should be stored. It then uses equals() to compare objects in the relevant bucket.
When two objects are logically equal but have different hash codes, they may be stored in different buckets. In that case, the HashSet may not compare them using equals(), allowing duplicate logical records.
How is the problem corrected?
The Student class must override both equals() and hashCode() using the same identifying field, which is regNo.
The registration number should also be immutable to prevent the object's hash code from changing after insertion.

5. Alternative Concept and Complexity Analysis
Instead of using HashSet<Student>, the attendance system can use TreeSet<Student> or HashMap<String, Student>.
A. Using TreeSet with Comparator
TreeSet stores elements in sorted order and prevents duplicates according to its comparison result.
import java.util.Comparator;
import java.util.Set;
import java.util.TreeSet;

public class TreeSetDemo {

    public static void main(String[] args) {

        Set<Student> students = new TreeSet<>(
            Comparator.comparing(s -> s.toString().split(" ")[0])
        );

        students.add(new Student("192311001", "Arun"));
        students.add(new Student("192311002", "Divya"));
        students.add(new Student("192311001", "Arun"));

        System.out.println("Unique students: " + students.size());
    }
}
For a cleaner reusable design, the comparator should access a registration-number getter rather than extracting it from toString().
B. Using HashMap with registration number as key
HashMap can store the registration number as the key and the Student object as the value.
import java.util.HashMap;
import java.util.Map;

public class HashMapDemo {

    public static void main(String[] args) {

        Map<String, Student> students = new HashMap<>();

        students.put(
            "192311001",
            new Student("192311001", "Arun")
        );

        students.put(
            "192311002",
            new Student("192311002", "Divya")
        );

        students.put(
            "192311001",
            new Student("192311001", "Arun")
        );

        System.out.println("Unique students: " + students.size());
    }
}
When the same registration number is inserted again, the existing value is replaced instead of creating another entry.
Complexity comparison
Let n represent the number of unique students.

Operation	HashSet	TreeSet		HashMap
Insert student	O(1) average	O(log n)		O(1) average
Check duplicate	O(1) average	O(log n)		O(1) average
Search student	O(1) average	O(log n)		O(1) average
Store n students	O(n)	O(n)		O(n)
Space complexity:
•	HashSet: O(n) for storing unique student entries.
•	TreeSet: O(n) for storing tree nodes and their references.
•	HashMap: O(n) for storing key-value entries.
HashSet and HashMap can have O(n) worst-case lookup behaviour in heavily colliding hash buckets, while TreeSet maintains O(log n) lookup and insertion complexity.


Alternative design decision

Requirement	Recommended structure
Store unique students without requiring sorted order	HashSet
Store unique students in registration-number order	TreeSet
Retrieve student details directly using registration number	HashMap

For a college attendance system, HashSet is suitable when the main requirement is to avoid duplicate attendance records. HashMap is a good alternative when the system frequently retrieves student information using registration numbers.
6. Final Conclusion
The experiment demonstrates that overriding equals() alone is insufficient when using hash-based collections. Both equals() and hashCode() must follow their contract to ensure correct duplicate detection.
In the college attendance system, the registration number is the unique identifier of each student. Therefore, both methods should use regNo for comparison and hash-code generation. The field should be immutable to avoid unexpected behaviour after insertion.
Final recommendation: Use HashSet<Student> with correctly implemented equals() and hashCode() for attendance de-duplication. Use HashMap<String, Student> when direct student lookup by registration number is also required.
