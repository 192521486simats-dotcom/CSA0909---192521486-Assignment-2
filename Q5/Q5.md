1. Inputs and Outputs
Problem context: An inter-college sports leaderboard ranks teams using three conditions:
1.	Higher points rank first.
2.	If points are equal, higher goal difference ranks first.
3.	If both are equal, team name is considered alphabetically.
The same ranking component should later support players, colleges and quiz teams.
Input:
•	Team name.
•	Points.
•	Goal difference.
•	A comparator defining ranking rules.
Output:
•	Teams arranged in the correct ranking order.
•	A reusable generic leaderboard.
•	A sorted copy that does not change the original list.

2. Prediction and Design Reasoning

A. Comparable vs Comparator
Comparable
•	Defines the natural ordering inside a class.
•	A class implements Comparable<T>.
•	Suitable when a type has one standard ordering.
Comparator
•	Defines ordering outside the class.
•	Supports multiple ranking rules for the same type.
•	Makes the leaderboard reusable for different requirements.
Design decision: Use Comparator because the ranking rules may change for teams, players, colleges and quiz participants. The Team class should not be forced to contain one permanent ranking rule.

B. Multi-field comparison
The required order is:
Points       → Descending
Goal Diff    → Descending
Team Name    → Ascending
A comparator can combine these conditions using Comparator.comparing() and thenComparing().
C. Generic class
Leaderboard<T> allows the same component to work with different object types.
Comparator<? super T> accepts a comparator for T or one of its supertypes.
List<? extends T> is useful when accepting a list containing objects of type T or its subclasses. It is not required for the basic add(T) method in this implementation.

5. Correctness Inquiry
A comparator must maintain a consistent ordering.
The correct comparator uses three levels of comparison:
1.	Compare points in descending order.
2.	If points are equal, compare goal difference in descending order.
3.	If both are equal, compare names in ascending alphabetical order.
This is called lexicographical comparison.
The comparator is transitive because each comparison follows the same ordered sequence of fields. If team A ranks above team B and team B ranks above team C, team A will also rank above team C.
It also returns zero only when all three ranking fields are equal.
Why does Bisons rank above Panthers?
Both teams have:
•	9 points.
•	4 goal difference.
Therefore, the comparator checks the final condition, team name. Since Bisons comes before Panthers alphabetically, Bisons receives the higher position.

6. Alternative Concept and Complexity Analysis

A. Using Comparable
If Team implements Comparable<Team>, the ranking rule can be defined inside the Team class.
class Team implements Comparable<Team> {

    final String name;
    final int points;
    final int goalDiff;

    Team(String name, int points, int goalDiff) {
        this.name = name;
        this.points = points;
        this.goalDiff = goalDiff;
    }

    @Override
    public int compareTo(Team other) {

        int result = Integer.compare(other.points, points);

        if (result == 0) {
            result = Integer.compare(other.goalDiff, goalDiff);
        }

        if (result == 0) {
            result = name.compareTo(other.name);
        }

        return result;
    }
}
Analysis:
•	Comparable defines one natural ordering for Team.
•	It is suitable when the ranking rule is permanent.
•	It is less flexible when different competitions require different ranking rules.

B. Using three stable sorting operations
Another approach is to sort the list three times:
1.	Sort by name alphabetically.
2.	Sort by goal difference descending.
3.	Sort by points descending.
Because Java's list sorting is stable, the earlier ordering is retained when later sorting considers two elements equal.
Pseudocode:
Sort by team name (A-Z)
Sort by goal difference (high to low)
Sort by points (high to low)

Complexity comparison

Let n be the number of teams.

Approach	Time complexity	Extra space
Comparator chain	O(n log n)	O(n) for copied list and sorting
Comparable	O(n log n)	O(n) for copied list and sorting
Three stable sorts	O(3n log n), equivalent to O(n log n)	Depends on sorting implementation

Design decision: Comparator is the best choice for this reusable leaderboard because different objects can use different ranking rules without modifying their original classes.

7. Final Conclusion
The generic leaderboard provides a reusable solution for ranking teams, players, colleges and quiz participants.
Using Comparator allows multiple ranking conditions to be combined in a clear and consistent manner. The generic class supports different object types, while ranking() returns a sorted copy without changing the original insertion order.
The correct comparator satisfies the required ranking rules, whereas the faulty comparator demonstrates why ignoring tie-breakers can produce incorrect results.
