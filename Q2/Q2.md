
1. Inputs and Outputs
Problem context: A music-streaming application allows users to create and manage playlists. Users can add songs, insert songs at selected positions, remove songs and directly access a song by its position.
The application currently uses ArrayList<Song> to store playlist data.
Input:
•	Song details such as song ID and title.
•	Playlist size.
•	Position at which a song must be inserted or removed.
•	Number of operations performed.
Output:
•	Updated playlist.
•	Inserted or removed song details.
•	Accessed song at a selected position.
•	Execution time for different list operations.

Objective: Compare ArrayList and LinkedList for playlist operations and evaluate whether ArrayDeque is a better choice for an Up Next queue.

2. Prediction and Design Reasoning

ArrayList
ArrayList uses a dynamically resizable array to store elements.
•	Adding a song at the end is generally fast.
•	Accessing a song by index is fast.
•	Inserting or removing at the front or middle requires shifting elements.
•	Iteration is efficient because elements are stored in a continuous array.
LinkedList
LinkedList uses nodes connected through references to previous and next nodes.
•	Adding or removing at either end is efficient.
•	Accessing an element by index requires traversal.
•	Inserting or removing in the middle requires locating the node first.
•	Each node requires additional memory for references.

Predicted comparison

Operation	ArrayList	LinkedList
Add at end	O(1) amortized	O(1)
Insert at front	O(n)	O(1)
Insert in middle by index	O(n)	O(n) to locate, O(1) to link
Remove at front	O(n)	O(1)
Remove in middle by index	O(n)	O(n) to locate, O(1) to unlink
Access k-th element	O(1)	O(n)
Full iteration	O(n)	O(n)

Prediction: ArrayList is expected to perform better when users frequently access songs by position and iterate through playlists. LinkedList is more appropriate when frequent additions and removals occur at the ends or when nodes are already located through an iterator.

5. Changed Condition – Up Next Queue

The application introduces an Up Next queue where songs are frequently added at both ends and removed from the front.
In this situation, ArrayDeque is more appropriate than ArrayList.
Reasons:
•	It supports insertion at both ends.
•	It supports removal from both ends.
•	It does not require shifting all elements when adding at the front.
•	It is designed for efficient queue and deque operations.
•	It does not allow null elements and is not thread-safe by default.

Example:
ArrayDeque<String> queue = new ArrayDeque<>();

queue.addLast("Song A");
queue.addLast("Song B");
queue.addFirst("Priority Song");

System.out.println(queue.removeFirst());
Output:
Priority Song
ArrayDeque is suitable for the Up Next queue, while ArrayList remains suitable for the main playlist.

6. Alternative Concept and Complexity Analysis

Operation complexity comparison

Operation	ArrayList	LinkedList	ArrayDeque
Add at end	O(1) amortized	O(1)	O(1) amortized
Insert at front	O(n)	O(1)	O(1) amortized
Insert in middle	O(n)	O(n) to locate	Not directly supported
Get k-th element	O(1)	O(n)	Not directly supported
Remove from front	O(n)	O(1)	O(1) amortized
Full iteration	O(n)	O(n)	O(n)

Space complexity

Data structure	Space used per element
ArrayList	One array reference per element, plus unused capacity when present
LinkedList	One node containing the element reference and previous/next references
ArrayDeque	One array slot per element, plus unused capacity when present



Alternative: Plain array with manual shifting
If a playlist were stored in a normal array, insertion and removal would require manually shifting elements.
Insertion example:
for (int i = size; i > position; i--) {
    songs[i] = songs[i - 1];
}

songs[position] = newSong;
size++;
Removal example:
for (int i = position; i < size - 1; i++) {
    songs[i] = songs[i + 1];
}

size--;

•	Accessing an element by index: O(1).
•	Inserting at the end when capacity is available: O(1).
•	Inserting or removing at the front or middle: O(n).
•	Iteration: O(n).
A plain array provides direct access but requires manual capacity management and shifting operations. ArrayList handles resizing automatically and is generally more convenient.

7. Final Design Decision
For the music-streaming application, ArrayList is a reasonable engineering choice for the main playlist because users frequently access songs by index, browse playlists and iterate through their songs.
However, if the application frequently inserts and removes songs at the beginning or middle using an already-positioned iterator, LinkedList may be considered.
When the application introduces an Up Next queue with frequent additions at both ends and removals from the front, ArrayDeque is the better choice.
Final recommendation:
•	Main playlist: ArrayList<Song>
•	Up Next queue: ArrayDeque<Song>
•	Frequent end operations with node-based manipulation: LinkedList<Song>
The choice should depend on the actual usage pattern rather than assuming one collection is always faster.
